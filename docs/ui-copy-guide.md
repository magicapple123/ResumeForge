## 1. 判定标准（核心）

### 1.1 一词一义：同一实体全站只有一个名称

一条实体只能有一个**中文正名**。同一实体的第二个说法一律算问题，哪怕它"读起来更好"。

| 判据 | 说明 |
|---|---|
| 同一实体 | 指向同一个数据记录 / 同一个页面 / 同一个按钮行为。判据：它们的**改动会同时发生**（改一处数据，另一处跟着变） |
| 允许的变体 | 只有两种：① 公文式指代（"简历"→"这份简历"）；② 在术语表登记过的**栏位专名**（见下条） |
| **专名与统称** | 一个概念层可以有**专名**（出现在它自己的控件标签上）与**统称**（出现在跨层叙述里）。规则：专名只许出现在该控件及其 Tooltip 内；一句话同时涉及多层时，**必须**用统称，不得用某一层的专名代指整体。（例：允许「版式」作为下拉标签，允许「排版设置已保存」，**禁止**「简历版式修改已保存」） |
| 检测方法 | 对同一实体 grep 出全部说法，≥2 个且能在同一批截图里出现 → 至少 P2；出现在**同一屏** → P1 |
| 反例 | 同一个模板选择器上并存四个词指两件事：标签「样式」、无障碍名「选择简历模板并预览效果」、相邻下拉「版式」、该下拉选项「模板自带」 |
| 正例 | 「彻底删除」（永久）与「删除」（软删入回收站）是两个**不同动作**，两个名字各自成立——不算一词多义，因为后果不同 |

### 1.2 动词优先：按钮写"做什么"，不写"这一步叫什么"

| 规则 | 判据 |
|---|---|
| 按钮 = 动词 + 对象 | 对象可省，当且仅当它已由所在区域唯一确定（表格行内「编辑」可省"简历"，弹窗 footer 不可省） |
| 不写名词按钮 | 「批量选择」「详情」「预览」这类**模式切换**按钮允许（它们是状态开关），须在术语表登记为"模式"而非"动作" |
| 不写空动词 | 见 §1.4 |
| 正例 | `删除所选`、`移入回收站`、`保存版式`、`去求职进度跟进`、`恢复默认` |
| 反例 | `okText="确定"`、`提交`、`继续`（未说明继续做什么） |

### 1.3 动作可预测：点下去会发生什么，必须写在按钮上

| 后果 | 按钮必须体现 |
|---|---|
| 数据被永久移除 | 用「彻底删除」+ `danger`；不得用「删除」「移除」「清理」 |
| 数据进回收站（可恢复） | 用「删除」；二次确认正文必须写"会移入回收站，可恢复" |
| 只是从列表/队列拿掉，数据仍在 | 用「移出」+ 容器名（`移出队列`） |
| 会覆盖已保存的配置 | 「保存」不够，须写明对象（`应用此版式`），或确认正文写清"旧设置会被替换" |
| 需要服务器重算/重排 | 用「重新生成」「重新排版」；不得用「刷新」（刷新只指重新取数） |
| 只改当前会话、不落库 | 不得用「保存」；用「应用」或「预览」 |

判定：把按钮文字念给一个没用过该产品的人听，他能说出"我的数据会变成什么样" → 合格；只能说"大概是保存吧" → 不合格。

### 1.4 去歧义：空动词禁令（硬约束）

| 禁用词 | 为什么禁 | 替代 |
|---|---|---|
| 确定 | 不携带后果信息，用户只能靠读正文 | 写成真实动作：`删除`、`移入回收站`、`覆盖保存` |
| 提交 | 系统里"提交"没有统一后果（提交表单？起任务？提交给谁？） | `保存`（落库）、`开始投递`（起任务）、`确认导入`（导入前确认） |
| 处理 | 后果未知 | 拆成具体动作（`重试`、`忽略`、`标记完成`） |
| 操作 | 同上；`操作失败` 是最典型的无信息错误提示 | 见 §4.6 |
| 执行 / 运行 / 继续 | 缺对象 | `开始投递`、`继续填表`、`重新生成` |
| 确认（单独作按钮） | 只表达"我同意"，不表达"同意之后做什么" | 二段式：`删除` / 正文写后果 |

例外：`okText="确定"` 仅允许出现在**纯选择类**弹窗且正文已含动作+对象+后果；「确定」作正文副词（"方向还不确定的机会"）不受限。

### 1.5 长度与语气

| 位 | 上限（中文） | 超限处理 |
|---|---|---|
| 按钮 / 菜单项 | 2–6 字 | 拆成 `主按钮 + 更多菜单项` |
| 弹窗标题 | ≤ 12 字 | 限定条件挪进正文 |
| 表头 | ≤ 6 字 | 用 Tooltip 补全称 |
| 占位符 | ≤ 20 字 | 说明挪到 `Form.Item extra` |
| 成功提示 | ≤ 24 字 | 细节放持久区域（列表/详情） |
| 错误提示 | ≤ 60 字 | 见 §4.6 两段式 |
| Tooltip | ≤ 40 字，一句完整话 | 需两句的用 Popover |

语气：陈述事实，不用感叹号（全库 UI 文案 0 处「！」，保持）；不用「哦/啦/呢/吧」（投投浮球等**拟人角色**台词豁免）；每句最多一个「请」，只用于表单校验与阻断性提示，连续两个「请」禁止；不承诺结果（"一定能通过 ATS"），只描述动作与已知事实。

### 1.6 大小写与标点

| 规则 | 正例 | 反例 |
|---|---|---|
| 英文缩写全大写、原样保留 | `PDF`、`Word`、`Markdown`、`HTML`、`A4`、`ATS`、`JD`、`AI` | `Pdf`、`word`、`ats` |
| 品牌/文件名保留官方拼写 | `Setup.exe`、`GitHub`、`English` | `setup.exe`、`Github`、`英文`（语言选项按惯例用英文本身） |
| 数字与量词之间加一个半角空格 | `3 页`、`已恢复 3 条`、`共 5 个岗位` | `3页`、`已恢复3条` |
| 数值范围用一字线、不带空格 | `1–3 页`、`40–69` | `1 - 3 页` |
| 界面元素名一律用直角引号「」 | `可在「回收站」里恢复` | `可在"回收站"里恢复` |
| 用户数据/变量值用弯引号 “” | `确定删除数据集“工作”` | 用「」包数据值（与 UI 名混淆） |
| 省略号用 `…`（U+2026） | `正在按新设置重新排版…` | `...` |
| 问号用于疑问句，全角 | `删除 3 份资料？` | 确认弹窗标题漏问号 |
| 按钮/表头/标题/占位符/Tooltip 末尾不加句号 | `搜索标题、正文或备注` | `搜索标题、正文或备注。` |
| 正文段落/错误/成功提示的完整句加句号 | `会移入回收站，之后可以在「回收站」里恢复。` | 缺句号 |
| 不得出现「正名（旧别名）」并列写法 | `版式` | `格式模板（版式）` |

### 1.7 数量与单位

| 实体 | 量词 | 现有依据 |
|---|---|---|
| 简历 | 份 | 81 处 |
| 资料 / 文件 | 份 | `BatchDeleteButton noun="份资料"` |
| 岗位 | 个 | `N 个岗位` |
| 条目 / 记录（台账、投递记录、收藏、提醒、内推、面经） | 条 | `已恢复 N 条` |
| 深挖 | 场 | `删除选中的 N 场深挖？` |
| 题目 | 道 | 7:2 多数 |
| 批次 | 个 | `N 个批次` |
| 尝试 / 投递次数 | 次 | `第 2 次尝试` |
| 页数 / 文件大小 | 页 / MB / KB | `1–3 页`、`上限 M 页` |

规则：**批量确认与成功提示必须"数量 + 单位"同时出现**（`删除选中的 3 份资料？`），只写数字不写单位禁止；单位不得口语化（"几个"禁止）。

### 1.8 双状态适配：什么时候必须进 `zh-CN.ts`

`src/i18n/cjkRatchet.test.ts` 守着"存量中文不许上涨"，所以新增中文不是"想放哪就放哪"：

| 情形 | 落点 |
|---|---|
| 同一条文案出现在 ≥2 个位置 | **必须** `t()`（例：`resume.format.label` 被视觉标签与 `aria-label` 共用） |
| 产品核心术语（术语表登记的名称） | **必须** `t()`（它们是词表，不是句子） |
| 需随语言变化的枚举（选项、档位、单位） | **必须** `t()` |
| 含插值/拼接的句子 | **必须** `t()` 整句 + 参数占位；**禁止**拆词块再拼（语言包注释第 3 条） |
| 只在单一文件出现一次、且不属上述三类 | 允许硬编码（贴近使用处更好读）；若触发 ratchet，加 `// i18n-ok: 理由` 行内豁免 |
| 纸面文案（小节标题、字段前缀） | 不得进前端语言包；去 `resume_labels.py` |

key 命名沿用既有规则：`<领域>.<对象>.<用途>`、全小写 kebab、禁中文当 key、禁拼句。

## 2.2 三层定名（裁决）+ 替换映射表

**裁决（PM 定，2026-10-22）**：分四层定名，各层专名互不复用，跨层叙述用统称。

| 层 | 含义 | 正名 | 完整名 | 禁用 | 界面上的位置 |

1. `ResumeMeasureControls` 的「随版式 / 随模板」这对提示**已经**用「版式」精确指 L2 并**靠它**与 L1 区分——改名会让这对提示失去现有区分度，还要连带改 2 处 + 测试。

3. 真正的歧义源不是 L2 叫「版式」，而是**L3 与统称也在用「版式」**。分层后「版式」只剩一个含义，歧义即消失。
4. 若主理人仍要 L2 改「预设」：**只需把下表 L2 段的"改为"一列整列替换为「预设」**，L1/L3/L4 不动，裁决结构不受影响。

## 2.4 后端用户可见消息的口径（主理人实测：139 条唯一 detail）

## 2.5 导航项命名规则（v1.2 新增，回应 N1–N3）

| 规则 | 判据 | 现状 |
|---|---|---|
| **N-a 名词优先** | 导航名指向"一个地方"，用名词短语（对象 + 场所）：岗位广场、简历中心、投递台、资料箱、事实台账、回收站 | **15 / 17 合规** |
| **N-b 流程型例外** | 功能若**没有单一对象**、价值在"一连串动作"（开启浏览器→识别→代填；开始→作答→复盘），允许动宾，但必须「领域词 + 动作词」两段式、≤4 字 | **2 项**：网申填表、模拟面试 |
| **N-c 容器名须可枚举** | 容器型导航（点进去是多个模块）必须满足两条：① 页头一句话列出模块；② 导航 Tooltip 与页头那句一致 | 工作台（2 个模块） |
| **N-d 易混项须有 Tooltip** | 同一分组内两个导航名共享 ≥2 个连续汉字，必须各给一句职责 Tooltip，且两句必须**互指对方**（A 里说明"不是 B"） | 我的资料 / 资料箱 |

### N1 裁决：「工作台」保留（B 变体），但必须同时消灭「技能」的双入口

**事实核对**（比原假设更复杂）：
- 页面确有两个模块：`SkillsPage.tsx` 的 Tabs = 「助手技能」+「简历模板」（后者渲染 `TemplateWorkbench`，其中含「模板」「版式」两张卡）。
- 页头已有一句列出两模块：「技能决定助手怎么回答，简历模板决定简历长什么样——两件事都在这里管。」→ **N-c ①已满足**。
- **自制版式在 `工作台 → 简历模板 → 版式` 卡里**（`FormatTemplateEditorModal`「自制版式」），**不在「模板市场」**——`market` 字段前端无任何渲染（见术语表 #14）。所以 `ResumeTemplateControls.tsx:183` 那句 Tooltip 指的地点是对的，但**指路太粗**。
- **真正的缺陷（比命名更严重）**：`技能` 有两个管理入口且都能改同一份数据——`工作台 → 助手技能`（新建/导入/编辑/删除/启用，全套 CRUD）与 `设置 → AI 模型 → 助手能力 → SkillsCard`（导入/开关/删除/查看）。用户不知道哪个是权威。

**裁决**：**不选 A**。改名「技能」会让「简历模板」这个已存在的模块挂到一个叫"技能"的地方，属于用改名掩盖结构问题，反而制造新的 P1。取 **B + 三项必须同时做**：

> **v1.3 代码证据（可复核，勿凭术语表推断）**：
> `grep -rn "TemplateWorkbench" frontend/src` → 生产代码**只有一个渲染点**：`pages/SkillsPage.tsx:276`，位于 `templates` Tab（label「简历模板」）。
> `pages/SkillsPage.tsx` 由 `App.tsx:438` 的 `<Route path="/skills" element={<SkillsPage />} />` 挂载。
> 「自制版式」的组件 `FormatTemplateEditorModal`（title「自制版式」）从这里进入 → **确认入口是 `/skills`（工作台）→ 简历模板 Tab，不是「模板市场」**（后者前端无渲染，术语表 #14）。
> 因此 `ResumeTemplateControls.tsx:183`「可以在工作台里自制更多版式」**方向正确**，只需补路径；若把导航改名为「技能」，这句话立刻变错。

| 做什么 | 具体 |
|---|---|
| ① 导航 Tooltip（补 N-c ②） | `助手技能与简历模板：前者决定助手怎么回答，后者决定简历长什么样` |
| ② 页头保持现有一句（已合规） | 沿用 `SkillsPage.tsx` 现有副标题，不再加第二句说明 |
| ③ 消除双入口 | 设置页 `SkillsCard` 改为**只读摘要 + 「去工作台管理」链接**（等价的另一选择是整块删除）。仅改文案不够——两处都能写，用户迟早会遇到"我在这里关了，怎么那里还开着" |

**`ResumeTemplateControls.tsx:183` 那句 Tooltip 的处理**：**保留原文，不要改**（「工作台」指向正确，见 §2.1.1）。可选优化（**P3，非必须**）：补全路径为 `版式控制行高、页边距与强调色；可以在工作台 → 简历模板里自制更多版式`，词本身不动。**明确不要**改成「模板市场」：那个入口在界面上不存在（术语表 #14），改了就是指向虚空。

### N2 裁决：两个都不改名，补 Tooltip + 强制"限定用语"

**理由**：改名成本不是问题（C1–C2），问题是**没有更好的名字**：
- 「我的资料」→「个人档案」更准，但要连带导航 + 页头 + 指南 + README + 测试（C3），且"档案"在求职语境里偏行政口吻。
- 「资料箱」→「材料箱」只是把「资料/材料」这组近义词换了个方向，仍在同一语义场里打转，还会与文档 21 处、README 10 处的"资料箱"打架（R5 要四处同改）。
- **结构性优势**：两者靠**限定结构**区分——「我的」= 归属，「箱」= 容器。这个差别是可教的，只是现在没教。

**裁决**：保持现名 + 两条硬约束：

| 做什么 | 具体 |
|---|---|
| ① 导航 Tooltip（N-d） | 我的资料：`你的个人档案：基础信息、教育、经历、技能；简历与网申表单都从这里取数`<br>资料箱：`与求职相关的材料：证书、作品、公司信息、链接、笔记；不是你的个人档案` |
| ② 正文限定用语 | 提到个人档案**必须带限定词**（「个人资料」「简历资料」「网申资料」「资料页」），**禁止裸用「资料」**指它；裸「资料」只指资料箱里的一条（术语表 #15），量词固定「份」 |

注意：`我的资料` 页内的两个 tab 已经叫「简历资料」「网申资料」，**符合本条**（限定词齐全），无需改。真正要改的是 `MaterialsPage.tsx:105` 的 `资料已更新`——这句裸用「资料」，在同一产品里可指两样东西（映射表之外新增一条：改 `已保存资料「X」`）。

### N3 裁决：「网申填表」保留，但它是**第 2 个**流程型例外，不是唯一例外

先纠正前提：`模拟面试`（`navigationConfig.ts:71-76`）同样是动宾结构（模拟 = 动词）。全站 **2 / 17** 是动宾，不是 1 / 17。这一点很关键——**两个例子让"例外"变成了规律**，所以不需要为「网申填表」单独开特例，把 N-b 写进规则即可。

为什么这两个可以动宾而其它不行：它们的**对象不唯一**。
- 网申填表：对象是"一整套外部网站的未知表单"，无法用一个名词概括（叫「网申表单」会把工具说成数据）。
- 模拟面试：对象是"一场还没发生的对话"，叫「面试练习」反而弱化了"AI 扮演面试官"这个差异点。
- 反例对照：`投递` 有明确对象（岗位）→ 必须名词化（投递台）；`清理` 有明确对象（回收站）→ 不单独占导航。

**裁决**：保留「网申填表」。候选被否的理由：「网申」太泛（与投递同义，用户分不清两页差别）；「网申助手」与「求职助手」撞 2 字且助手在产品里专指聊天（术语表 #32）。

## 4. 文案位分规则

`<>` 为必填槽位，`[]` 为可选。

### 4.1 按钮
- 模板：`<动词><对象>`，2–6 字，无句号，无数量（数量进正文）。主按钮承担唯一主动作；同区不得有两个「保存」语义的按钮。
- 正例：`删除所选`、`去求职进度跟进`、`保存版式`　反例：`确定`、`处理`、`批量选择并删除`

### 4.2 弹窗标题
- 模板：动作型 `<动词><对象>`；确认型 `<动词><对象><数量>？`；内容型 `<对象>[ · <限定>]`。
- 正例：`生成通用简历`、`选择简历模板`、`删除选中的 3 份资料？`、`模板预览 · 简洁`
- 反例：`确定删除该岗位？`（冗余且缺数量）、`提示`、`操作确认`

### 4.3 弹窗正文
- 模板：`<会发生什么>；<什么不会被改变 / 能不能恢复>。` 必须含一条**边界说明**。
- 正例：`会移入回收站，之后可以在「回收站」里恢复。`／`通用简历不针对任何岗位：系统会完整使用你的资料，原始资料不会被修改。`
- 反例：`此操作不可撤销。`（只说危险，不说对象与范围）
- **例外：没有恢复入口的操作，不许套回收站话术（v1.5 新增）**。判据只有一条——**它能不能被「回收站」恢复**。能，正文统一写 `会移入回收站，之后可以在「回收站」里恢复。`；不能，必须如实说明"没有恢复入口"，并给出一条**可执行的补救动作**。
  - 实例：删除数据集。`backend/app/api/trash.py` 里没有任何 dataset 类型，`delete_dataset()` 只把文件挪到 `datasets/.trash/`、界面上也没有恢复端点——所以正文写「数据集会移出列表，界面上没有恢复入口；删除前请先导出备份。」，而不是回收站话术。
  - 反例：给数据集删除写「会移入回收站，可以恢复」——承诺了做不到的事，比不写后果更糟（§2.4 同一原则：只描述已知事实）。

### 4.4 二次确认（三段式，硬约束）
- 结构：**动作 + 对象（含数量）+ 后果（含可逆性）**，缺一段即不合格。标题 = 动作+对象+数量+`？`；正文 = 后果+可逆性；okText = 具体动作。
- **例外：数量让标题超 12 字时（v1.5 新增）**。§1.5 要求弹窗标题 ≤12 字、§1.7 又要求"数量 + 单位"出现在批量确认里——数量一长两条就互斥（`把选中的 2 个岗位移出队列？` 已 15 字，而 `删除选中的 120 条提醒？` 必然更长）。此时的规则是：
  1. **标题只写「动作 + 对象」**，数量**移入正文**；正文仍须含对象 + 数量 + 后果（三段式一段都不能少）。
  2. 判断顺序固定：**先保证标题 ≤12 字，再保证数量出现在正文**。两处都省 = 不合格；标题写了数量且不超长，正文可以不再重复。
  3. 反过来也成立：标题里不写数量，正文里就必须写；不许两边都省。
  - 正例：标题 `移出队列？` + 正文 `把这 12 个岗位从队列里拿掉，岗位与投递记录都不会被删除。`
  - 反例：标题 `把选中的 12 个岗位移出队列？`（15 字，超限）与"标题省数量、正文也不提数量"（用户不知道会影响多少条）。
- 正例（现成典范，`BatchDeleteButton.tsx`）：标题 `删除选中的 3 份资料？` / 正文 `会移入回收站，之后可以在「回收站」里恢复。` / okText `删除`
- 反例：`确定把选中的 5 个岗位移出队列？`（`ApplyQueuePanel.tsx:345`，冗余"确定"）、`确定删除这条记录？`（`ResumeTable.tsx:83`，对象未命名）、`确定删除该岗位？`（`JobTable.tsx:231`）
- 危险操作（彻底删除/清空/删数据集）必须：`danger` + 正文含"无法恢复" + 标题含数量或对象名。

### 4.5 成功提示
- 模板：`已<动作><对象>[，<可去哪里查看/恢复>]`。**必须含对象与结果**。
- 正例：`已恢复 3 条面经`、`已移入回收站，可在「回收站」里恢复`、`已恢复 4 条，1 条恢复失败，请重试`
- 反例：`已删除`（6 处，无对象）、`操作成功`、`资料已更新`（`MaterialsPage.tsx:105`，"资料"同时可指个人档案与资料箱条目）

### 4.6 错误提示（前后端分工）
- 前端两段式：`<发生了什么>：<原因>。[<怎么办>]`；第二段仅在**同屏已有明确重试按钮**时可省。
- 后端 `detail` 只出第一段的原因（见 §2.4），由前端拼：`<区域>加载失败：<detail>。可以点「重试」再试一次。`
- **共用一套句式**：`reason + action` 的两段结构在 `api/errorGuidance.ts` 已实现（「原因 · 建议 · 编号」三段，编号取 `requestId` 前 8 位）。规则：**任何新增错误面必须走 `errorGuidance()`**，不得自拼 `message.error("保存失败")`；`errorGuidance` 里的 `reason` 遵守 §2.4 句式，`action` 必须是可执行动作（`重试`、`确认后端已启动`、`调小范围`）。
- 正例：`岗位不存在或已被删除`（112 次主流句式）、`请求等待超时` + `请重试；数据量大的导出/生成可稍后再试或调小范围`
- 反例：`这场深挖记录已不存在`（句式分叉）、`操作失败`、`保存失败`（无原因无出路）
- 禁止把 stack trace、SQL、英文原文、裸 HTTP 状态码抛给用户。

### 4.7 空态
- 模板：`还没有<对象>` + `[一句为什么/数据从哪来]` + 一个主行动作按钮（动词+对象）。
- 硬约束：**不得用方位词指路**（"右上角""下方"）——按钮位置随响应式变化；要么内嵌按钮，要么写明按钮名并保证同屏可见。
- 正例：`还没有通用简历` + 按钮 `生成通用简历`
- 反例：`资料箱还是空的，点右上角「放入资料」开始`（`MaterialsPage.tsx:273`）、`还没有自制样式模板。点右上角「复制改一份」从内置模板开始。`（`TemplateWorkbench.tsx:256`）
- 空态与错误态必须可区分：没数据用 `EmptyState`，请求失败用 `ErrorState`。
- **执行纪律：改共享文案常量前先 grep"这句话"，改完再 grep 两次（v1.5 新增）**。
  1. 改之前，用**当前文本片段** grep 一遍，把全部命中列出来，逐条判定是"引用常量"还是"手写副本"；
  2. 改完用**新文本** grep 一次（确认引用都跟上了），再用**旧文本** grep 一次（确认没有漏网副本）；
  3. 找不到该元素真名时，改用**任务语**（"导出后…"），不要硬编一个名字，也不要退回方位词。
  - 实例：`components/resume-preview/config.ts` 的 `OVERFLOW_NOTE` 已改成「先收紧**排版**或增加页数才能看全」，但 `ExactPreviewPanel.tsx:346` 里有一份手写的**前缀变体**（带动态页数）仍是「先收紧**版式**」——同一个弹窗里两种写法。成因是改的时候以"常量"为单位搜索而不是以"句子"为单位：常量改完，旧文本已经搜不到了，漏掉的副本反而隐形。

### 4.8 占位符
- 模板（搜索）：`搜索<字段1>、<字段2>或<字段3>`；（输入）：`<名词短语>` 或 `输入<对象>`。不加句号、不加冒号、不写规则说明（说明进 `extra`）。
- 正例：`搜索标题、正文或备注`　反例：`留空则自动命名为「姓名-通用简历-时间」`（规则塞进 placeholder，超 20 字会被截断）

### 4.9 菜单项
- 模板：2–4 字动词（对象由所在行确定时可省）。顺序固定：`查看 → 编辑 → 复制/移动 → ── → 危险项（danger）`。
- 正例：`编辑` / `移出队列` / ── / `彻底删除`　反例：菜单里出现 `确定`、`处理`；危险项与普通项混排无分隔。

### 4.10 表头
- 模板：名词，≤6 字，需要时带单位；同一列不得既是"时间"又是"日期"。
- 正例：`创建时间`、`投递批次`、`状态`　反例：`时间`（创建还是更新？）

### 4.11 工具提示（Tooltip）
- 模板：一句完整话，说明"这是什么 / 为什么这样 / 点了会怎样"，≤40 字，句末不加句号。功能提示一律用 `Tooltip`；原生 `title=` 只用于截断文本的完整值。
- 正例：`版式控制行高、页边距与强调色；可以在工作台里自制更多版式`　反例：把唯一可发现性入口写进 `title=`（触屏永不显示）。

### 4.12 无障碍名（`aria-label`）
- 模板：`<动词><对象>[ · <可区分限定>]`；icon-only 按钮**必须**有，不得只重复图标语义。
- 正例：`把教育经历上移`、`调整简历板块顺序`、`选择简历模板并预览效果`、`更多操作`
- 反例：`更多`、`按钮`；与视觉标签相同却未带对象（两处下拉都叫「选择」）。
- 同一编辑器内多个下拉/开关，`aria-label` 必须能唯一定位（供测试 `getByRole({name})` 使用）。

### 4.13 跨页引用界面文案（v1.2 新增，回应 N4）

任何在 A 处描述 B 处按钮的文字（使用指南、Tooltip、错误补救建议、空态指路、助手工具名），都算**引用**。硬约束三条：

| 规则 | 判据 |
|---|---|
| **R-1 逐字一致** | 引用必须与目标按钮/菜单项的**最终渲染文本完全相同**（含「」包裹），不得改写、缩写、补字 |

| **P-3** | 升级 antd 主版本后，**必须**复核本表（一次 grep 即可），因为废弃项会随版本增加（6.x 就把 `Alert.message`、`notification.message` 一并降级）。 |

| **A. grep 守卫（推荐）** | 在既有守卫测试目录新增 `antdDeprecatedProp.test.ts`：扫描 `src/**/*.tsx`（排除 `.test.tsx`），按判定表正则命中即失败；与 `antdStaticGuard` 同一种形态，纯文本扫描约 25 行 | **C1** | **可行且不易腐烂**：判定表只有 2–3 行，随版本升级才需要改 |

**怎么数才能数准（v1.5 新增，含排除项）**：

1. 按**元素块**扫，不按行扫。从 `<Alert`（或 `notification.`）起，配平 `{}`、`()` 与引号直到该元素结束，再在里面找目标属性。本项目大量属性是换行排列的：`grep "<Alert" | grep "message="` 只得 41，按元素块扫才是 134/135——**按行正则数任何"属性/参数"都会漏**。
2. 排除项（三者都不算违规，也不进统计）：
   - `fireWebNotification(payload.message)`（`TaskCompletionNotifier.tsx:29`）是**浏览器原生通知**，不是 antd，同名不适用本文判定表；
   - 自定义组件的同名 prop（`<MyComp message={…} />`）——判定表只覆盖 antd 组件；
   - 注释与文档字符串里举例的写法（`// 以前用 message=` 之类）。
3. 计数以**元素块**为单位报数（"131 个 `Alert` 用 `title`、4 个用 `message`"），不要报"行数"。

### 4.15 附注：`title` vs `message` 这类"API 记忆陷阱"的一般化（写给执行方）

本次错误（v1.1 判"`title` 不生效"）的成因是**用旧主版本的 API 记忆替代了当前 `.d.ts`**。规范层面的通用约束：

1. 凡是"某属性是否生效/是否推荐"，**唯一依据是 `node_modules` 里当前版本的类型定义**；文档、记忆、其他项目的经验都不得作为依据。
2. 凡是给出"某处不会渲染"这类**结论性判断**，必须附上可复现的证据（文件:行 + 原文），否则只能写成"疑似，待核实"，不得进 P0/P1。
3. 成员与主理人结论冲突时，以**能复现的一方**为准；本次即主理人实测推翻成员判断（见 §8 #7）。

### 4.16 按需下载的内置资源（v1.4 新增，2026-11：内置思源黑体）

"应用自带某个资源"与"按需下载某个资源"是两种事实，文案不能混写——内置字体属于后者：

1. **说明体积与来源**。用户点「下载」之前有权知道要拉多大、能不能商用（字体还要说授权）。正例：
   `联网下载，不占安装包体积。由 Adobe 发布，采用 SIL Open Font License 1.1，个人与商业文档均可免费使用`。
2. **下载按钮不写方位词**。文案里不出现"点右上角的下载""下面那颗按钮"这类位置描述——位置随响应式
   变化，控件靠自身可访问名定位（见 §4.12）。指路只写路径（`设置 → 应用 → 简历字体`）。
3. **下载中要给进度分母**（`下载中… 12.4 MB / 32 MB`），拿不到总量时只报已下载量，**不要编分母**。
4. **失败要说原因 + 下一步**：`下载思源黑体失败：{原因}。可以点「重试」再试一次。`——后端给的中文原因
   原样透出，它是用户唯一能据以行动的线索。
5. **直删类删除要写明"没有恢复入口"**：内置字体文件删了不进回收站，正文必须写
   `字体文件会被直接删掉，界面上没有恢复入口。`，不许套回收站话术（见 §4.3 / §4.4 的例外）。

## 5. 严重度分级

### 5.1 判定维度（按顺序回答，第一个"是"决定级别）

| 序 | 问题 | 若是 → |
|---|---|---|
| 1 | 按文案字面理解去操作，会不会**丢数据、作用于错误对象、或无法撤销**？ | **P0** |
| 2 | 同一**屏幕内**，同一实体是否出现两个名字 / 同一动作两个说法，且用户会以为这是两件事？ | **P1** |
| 3 | 用户是否**卡住**（不知道下一步做什么）——错误提示没有出路、空态没有行动、确认不知后果？ | **P1** |
| 4 | **跨页面**同一实体/动作名称不一致，但不改变理解（不误操作、不卡住）？ | **P2** |
| 5 | 只是措辞不够好（长度、语气、标点、量词、语序），原意准确且唯一？ | **P3** |

### 5.2 四级定义与处理要求

| 级别 | 定义 | 典型样本 | 处理 |
|---|---|---|---|
| **P0** | 文案与后果不符，或同屏两处同名不同义且都危险 | 按钮写「删除」实际永久删除；「清空回收站」正文未写"无法恢复"；`删除` 与 `彻底删除` 在同一菜单无分隔且文案相近 | 阻断发布，当轮修 |
| **P1** | 同屏自相矛盾，或用户会卡住 | 同一控件四词指两事（§2.1）；`确定删除这条记录？`；`操作失败`；`已删除`（无对象） | 本轮必修 |
| **P2** | 跨页面不一致，理解不受影响 | 后端 5 处 `已不存在` vs 112 处主流句式；`重新加载` vs `刷新`；`创建` vs `新建`；`台账条目` vs `台账记录` | 排期修，同领域批量一次改完 |
| **P3** | 措辞优化 | `批量选择并删除` 过长；`Pdf`；`...`；`条题` vs `道题`；说明塞进 placeholder | 顺手改，不单独排期 |

### 5.3 让不同人得出同一结论的三条补充判据

1. **可复现性**：判定必须给出"页面 + 截图 / 文件:行号"；给不出则降一级（影响面未确认）。
2. **两处即可一致**：两个不同人在同一屏内看出"这是两件事"→ P1；只有一人觉得"读起来别扭"→ P3。
3. **不叠加升级**：同一根因在 N 个文件出现，算**一条** P 级问题（记录 N 个位置），不因数量多升到 P0；升级只看后果。

### 5.4 成本轴：只决定"分几次改"，不决定"改不改"

主理人实测 2026-10-22：前端 **298** 个测试文件、**293** 个含中文断言；中文 `getByText` 断言 **665** 处、`{ name: "…" }` 查询 **804** 处 → **任何一处按钮改名，平均连带改 1–3 处断言**。

因此严重度只按 §5.1 判（用户受害程度），**不得**用"改起来贵"去降级——那会让"贵但严重"的问题永远不修。成本单独成轴，决定排期与切片：

| 成本 | 判据 | 典型 |
|---|---|---|
| **C1 单点** | 只改一处常量/通用组件，测试影响 ≤1 文件 | `BatchDeleteButton`、`ErrorState.retryLabel`、`EmptyState` 默认文案 |
| **C2 局部** | 同领域 3–10 处，测试影响 2–5 文件 | 本次 §2.2 映射表整体（23 处源码 / 9 文件） |
| **C3 批量** | 跨领域 >10 处，测试影响 >5 文件 | 若要全站取消「版式」字样（含 L2 改名） |

| P × C | 排期规则 |
|---|---|
| **P0 × 任何** | 立即修。C3 也要切出"最小可发布切片"（先修最危险那一条，其余同 PR 跟上） |
| **P1 × C1/C2** | 本迭代整条改完 |
| **P1 × C3** | **拆两步**：第一步只做不触碰共享锚点的局部补丁（补对象名、补后果、补数量），第二步再做批量改名 |
| **P2 × C1/C2** | 排期，按领域凑成一个 PR |
| **P2 × C3** | **必须先做锚点收敛**（§6 R6），收敛完成后再改名；不收敛不许开工 |
| **P3 × C3** | 不做 |

## 6. 冲突裁决原则

**序号即优先级。**

### R1 先问"是不是同一实体"，不要为了整齐把两个概念并成一个
- 只有**改动会同时发生**的才是同一实体（模板 vs 版式：换模板时版式默认值可能变，但两者各自独立可调 → 两个实体，不能合并）。
- 「版式」（输入）与「版面」（输出）、「排版参数」（逐项）与「版式」（一次套用）都不能合并，只能分层定名。
- 反例风险：把「彻底删除」统一成「删除」，会直接制造 P0。

### R2 安全与数据正确 > 一致性 > 简洁 > 语气
- 宁可保留一处不一致，也不要把"可恢复"写成"删除"。

### R3 统一优先于"更好"，但"更好"要说得出判据
- 两个说法都准确时，取**出现次数多、且与数据/路由/后端命名一致**的那个；不以个人语感为准。
- 例：`不存在或已被删除`（112 次、解释了"为什么看不到"）胜 `已不存在`（5 次）。
- 例：L1 取「模板」而非「样式」——界面可见字符串 98 : 47（主理人实测），且后端实体名是 `template`。

### R4 界面改名不改内部命名
- 改叫法时**不动**：路由 path、DB 列、API 字段、类型名、文件名、测试 fixture（`data/datasets`、`format_name`、`template`、`resume.format.label` 这个 key 本身）。
- 内部命名与界面名不一致本身不是缺陷；**界面**必须只用术语表正名。
- 例外：内部名会经异常消息泄到界面时，在边界处映射成中文正名，不改内部名。

### R5 已被 README / 用户指南 / 官网引用过的文案
- 判据：`grep` 到 `README.md`、`docs/user-guide.md`、`frontend/src/components/userGuideSteps.ts` 有同一说法。
- 处理：**以正名为准，文档跟着界面改**，不迁就存量。理由：文档与界面各叫一个名字，本身是 P1（用户会以为两个功能）。
- 允许的文档写法：`正名` 或 `正名 + 技术/英文括注`（`版式（format preset）`，便于开发者与搜索）。
- **禁止**：`正名（旧别名）` 并列写法（`格式模板（版式）` 就是现存违例）。
- 选定后**同一提交内**同改：界面 → `userGuideSteps.ts`（就地改措辞，不新增步骤，`AGENTS.md` 第 310 行）→ `docs/user-guide.md` → `README.md`（注意 `## ✨ 功能特性` 的行数守卫）→ `CHANGELOG.md`。
- 实测口径差（主理人实测）：`docs/user-guide.md` 模板 61 / 版式 34；`README.md` 模板 10 / 版式 4。与 L1=模板 的裁决**同向**，文档层只需处理 L3/统称那部分「版式」（约 7 处），不需要整体改口径。

### R6 改动会打挂测试断言时（本项目高发，实测有数）

| 情形 | 处理 |
|---|---|
| 断言只"钉住当前实现"（`getByText("已删除")`） | **允许改断言**，随实现一起改；改后 `grep` 复查该文件，确保没删掉整段用例 |
| 断言表达**产品契约**（草稿与精确预览"必须用同一套措辞"、`userGuideSteps` 的 path 与路由对应、`README_FEATURE_KEYS` 双向比对） | **不许为过测试而放宽/删除断言**；两边必须同时对 |
| 守卫测试（`cjkRatchet`/`antdStaticGuard`/`spinOutletGuard`/`noAutoShrinkGuard`/`noAutoShrink` 后端那条） | 不因文案改动豁免；新增硬编码中文触发 ratchet 时走 `// i18n-ok: 理由`，不许改阈值 |
| 一次改动连带测试 >5 文件 | 按领域拆成多个 PR（术语表 → 动词表 → 单位标点），每个 PR 只带自己的测试改动 |

**锚点收敛（P2×C3 的开工前置）**：改名成本与"文案出口数量"成正比。
1. 先把同一句文案收敛到**唯一出口**（常量、`EmptyState`/`ErrorState` 的默认 props、或 `zh-CN.ts`）。收敛把"改 N 处源码"降到"改 1 处源码"——断言数量不变，但源码爆炸半径归零。
2. 测试侧：**不承载产品契约**的高频文案，可在测试里引用同一常量（`import { COPY } from …`）而非字面量，后续改名 0 断言改动。
3. **承载契约的文案禁止用常量断言**（否则改了常量测试照样过，守卫失效）——必须保留字面量。
4. 顺序（固定）：**先改实现 → 跑相关 `.test.tsx` 拿失败清单 → 逐条改断言 → 每次 Edit 后 `grep` 复查被改处 → 最后全量 `npm test`**。

### R7 拿不准就不动
- 走不到本文件任何一行的，写进 §7，**不要在同一批改动里既改口径又改功能**。
- 同屏既有 P1 又有未定裁决时，先修 P1 中不依赖裁决的部分（补对象名、补后果、补数量），改名等裁决。

### 附：`Alert` / `notification` 的**废弃属性**残留（v1.3 已纠正方向，见 §8 #7）

**先认错**：v1.1–v1.2 在这里写过"antd `Alert` 的标题属性是 `message`，`title` 不生效，两处标题实际不渲染"——**这是 antd 4/5 的知识，在 6.6.5 上完全反了**。实测证据：

```
frontend/node_modules/antd/package.json  → 6.6.5
node_modules/antd/es/alert/Alert.d.ts:48  title?: React.ReactNode;        ← 正选
node_modules/antd/es/alert/Alert.d.ts:49-52
    /** @deprecated please use `title` instead. */
    message?: React.ReactNode;                                            ← 已废弃
```

所以 `<Alert title="…">` 是**正确写法**（全库绝大多数也是这么写的），真正要记的是反向的：**少数几处仍用已废弃的 `message=`**。

**全库实测（v1.3 逐元素扫描 `.tsx`、排除 `.test.tsx`）**：`<Alert` 元素 135 个，其中 `title=` 131 个、`message=` **4 个**：

| 位置 | 属性 | 级别 |
|---|---|---|
| `components/resume/ResumeChangeReviewModal.tsx:152` | `message={` | **P3**（仍兼容、能渲染，仅不一致 + 触发 deprecation 警告） |
| `components/resume/ResumeChangeReviewModal.tsx:176` | `message={` | P3 |
| `components/resume/ResumeDetailPreview.tsx:240` | `message="…"` | P3 |
| `components/resume/ResumeReviseModal.tsx:102` | `message={error}` | P3 |

同类问题不止 `Alert`——同一版本 `notification` 也把 `message` 标了 deprecated（`node_modules/antd/es/notification/interface.d.ts:40`）：

| 位置 | 现状 | 级别 |
|---|---|---|
| `components/TaskCompletionNotifier.tsx:36` | `notification[type]({ message: payload.message, … })` | **P3** |
| `components/RiskScanWatcher.tsx`、`SuggestionScanWatcher.tsx` | 已用 `title:`（正例，可参照） | — |

**判定口径**：这不是"文案不渲染"，而是"文案写在了已废弃的载体上"。**不影响功能、不影响可读性** → 按 §5.1 第 5 问，**P3**（顺手改，不单独排期）。原判 P1 是我判错了。

**为什么 `tsc` / eslint 抓不到**：`@deprecated` 只是 JSDoc 标记，TS 不报错，`tsc --noEmit` 全绿；项目也未启用 `eslint-plugin-deprecation`。所以这类问题只能靠 §4.14 的 grep 判据发现。
