# 运营手册（Operations Runbook）

面向维护者的日常运营与事故处置。与 `docs/architecture.md`（怎么搭的）、`docs/maintenance.md`（怎么维护代码）互补，这里只回答**出事了怎么办、发布怎么做、数据边界在哪**。

所有内容以**代码实际行为**为准书写；代码没有的能力不会出现在这里。

## 1. 发布清单

发布一个版本（`vX.Y.Z`）按以下顺序执行。**打勾即"有自动化守卫"，备注里如实标注未自动化环节。**

| 步骤 | 动作 | 自动化程度 |
| --- | --- | --- |
| ① 版本号 | 仓库根目录跑 `python scripts/bump_version.py`（按 Conventional Commits 判定幅度；破坏性变更显式传 `--bump`）。5 处版本号（backend config / frontend package.json + lock / README / CHANGELOG）由 `backend/tests/test_version_consistency.py` 钉住 | 脚本改文件，**提交与打 tag 由维护者手动执行**（脚本不 commit） |
| ② 全量验证 | 后端 `pytest -n auto --cov`（80% 门槛）+ `pip check` + `ruff check`；前端 `npm test` / `lint` / `typecheck` / `format:check` / `vite build`；macOS 启动链 `bash scripts/tests/test-macos-launcher.sh`、Windows `scripts/tests/Test-Start-ResumeForge.ps1` | 全部本地命令，CI 同样跑（三个 macOS 作业 + `windows-end-to-end`） |
| ③ 构建 | `scripts/Build-Release.ps1 -Ref <tag>`：`git archive` 打包受追踪文件 → 复开归档校验"必需文件都在、敏感文件绝不在" → 产物 `dist/ResumeForge-<version>.zip`。**校验失败的归档会被脚本直接删除，不进入发布** | ✅ 打包与内容校验自动化 |
| ④ 依赖清单（SBOM 性质） | `scripts/Generate-Sbom.ps1`：pip-licenses 产出 `THIRD-PARTY-NOTICES.txt` 与 `requirements-frozen.txt` 到 `runtime/sbom/`，随 CI 依赖审计作业上传 | ✅ 生成自动化；**只是第三方许可与锁定清单，不是 CycloneDX/SPDX 格式 SBOM**——如需标准格式需另接工具，当前未做 |
| ⑤ 校验和 | 计算发布 zip 的 SHA-256 并随发布说明公布，供用户下载后核对 | **手动**（无自动发布流水线） |
| ⑥ 签名 | **未做。** 发布 zip 无代码签名、无 GPG 签名，tag 亦无签名。完整性核对只能依赖 ⑤ 的 checksum（见 §7 威胁模型备注） | ❌ 未自动化、也未人工执行 |
| ⑦ 冒烟 | 干净检出/解包走一遍启动链：CI 的 `windows-end-to-end` / `macos-end-to-end` 从干净检出走完整启动并真的取一次前端入口模块；本地可用隔离演示库（`scripts/seed_demo_data.py --check` → 指定 `DATABASE_URL` 启动前后端）人工点一遍核心页面 | CI 自动 + **人工抽查靠自觉**，无强制冒烟关卡 |
| ⑧ 发布 | 在 GitHub 上以 tag 发 Release，附 zip 与 SHA-256 | **手动** |

## 2. 事故分级与响应

四级定义与各级的第一响应动作。判定从高往低走——拿不准时按更高一级处理。

### P0 — 数据不可读 / 疑似丢失
**定义**：用户数据库打不开、迁移后表结构损坏、备份恢复后行数对不上、数据文件被误删。
**响应**：
1. 立即停止发布任何新版本；若怀疑最新版本引入，撤下该 Release 的推荐标记。
2. 指引用户**保留现场**：不要重装、不要点"重建/修复"，复制 `backend/data/` 整目录（含 `-wal`/`-shm` 边车文件）做隔离副本。
3. 按仓库 `SECURITY.md` 之外的常规渠道（Issue）收集：`alembic current` 输出（若后端还能跑）、后端启动日志、SQLite 版本。
4. 修复优先走"从自动备份恢复"（§4）；迁移缺陷需写**新的前向修复迁移**，禁止篡改历史迁移文件。

### P1 — 隐私外发（隐私泄漏）
**定义**：个人资料/简历/照片/密钥离开本机的路径被打开（日志泄密、导出泄密、联网请求带多余数据）。
**响应**：
1. 确认泄漏通道与影响面（哪些版本、哪些数据类型）。
2. **可利用细节不在公开 Issue 披露**，遵循 `SECURITY.md` 的私下报告流程；补丁先行，公告后发。
3. 修复后补一类守卫测试（如日志脱敏测试见 `backend/tests/test_log_redact.py` 的先例），同类调用点全量排查而不是只修被报告的那一处。

### P2 — 功能不可用
**定义**：核心流程（简历生成、投递、备份导入导出）在正常配置下失败。
**响应**：
1. 在 Issue 里区分"配置问题/环境问题/代码缺陷"三类，让用户先跑启动链守卫测试与 preflight（后端启动自检必需资源）。
2. 缺陷确认后先建最小复现测试（红），再修复；破坏性修复方案需要迁移时回到 P0 流程。

### P3 — 性能劣化
**定义**：大库下接口/界面明显变慢，功能仍正确。
**响应**：
1. 用 `scripts/measure_api_perf.py` 复测对应端点（SLO fail-closed，p95 超阈值退出非零），拿到可比数字再动手；不要凭感觉优化。
2. 常见根因排查顺序：全量查询替代分页、N+1、`create_all` 掩盖的缺失索引、FTS 未命中回退 LIKE。

## 3. 诊断包最小化指引

请用户提供诊断信息时，**按需索取、明确排除**——诊断包里绝不应出现密钥与完整简历。

**可以收集**：
- `runtime/backend.log` / `backend.stderr.log` 的**出错时间窗前后各 50 行**（不要全量日志）；
- 后端启动横幅（版本号、数据目录、Alembic revision）；
- `GET /api/stats/storage` 输出（只有体积与文件数，无内容）；
- 操作系统版本、Python/Node 版本、启动方式（start.cmd / start.command / 手动）；
- 数据库**表行数统计**（可让用户跑 `scripts/seed_stress_data.py --check-only <库>` 的只读检查输出，它只报结构与计数）。

**必须排除 / 让用户先删掉**：
- `backend/.env` 与任何 API Key（日志里也不该有——落盘日志有脱敏守卫，但用户手动截图的终端输出可能带启动参数，提醒用户遮挡）；
- 完整简历/资料数据库（要结构信息时只要表清单与行数）；
- 导出的 HTML/PDF/JSON 简历文件、照片、附件。

**给用户的操作要求**：贴日志前自查一遍是否含姓名/手机号/邮箱片段；拿不准的行先遮再贴。

## 4. 备份恢复步骤

对应 PR-15 之后的备份包格式：包内 `manifest.json` 带版本链、各表行数与附件清单（逐文件 SHA-256）。日常恢复用**应用内「设置 → 数据 → 导入备份」**；以下是在应用打不开时的手动恢复流程。

**两种包形态（format 4 起，R16）**：单份数据集的包仍是平铺结构（`resume_forge.db` + `datasets/<id>.db` + `manifest.json`，format 1/2/3，带密钥时是 3）。「导出全部数据集」改成**嵌套整包**：外层 `manifest.json`（`format: 4`、`type: "collection"`）+ `README.txt` + `datasets/<id>.zip`，每个子 zip 就是一份完整的单数据集包，并在外层清单里登记 `sha256` 与 `size_bytes`。导入时逐份校验 SHA-256：坏一份只跳过那一份并在界面点名原因，其余照常恢复；至少一份成功即返回 200，全部失败才报错。**旧版本（≤1.0.2）会明确拒收 format 4**（提示先升级），format 1/2/3 的旧包仍可正常导入。外层 zip 不能再套第二层嵌套。

**应用内导入现在的语义（RR-03，2026-10-14 起）**：

- 导入是**先验后发布**：数据库在隔离候选文件中迁移校验，附件写入私有暂存并逐项检查大小、SHA-256、跨平台文件名和冲突。业务目录尚未发布；这不等于磁盘完全没有临时写入。严格恢复拒绝包内问题和导出时声明的不完整附件。
- **本机同名但内容不同的附件绝不被覆盖**：冲突被显式报出（这是与旧行为的最大差别——旧实现是"先 `open('wb')` 覆盖、写完再复核"，被篡改的包会把本机附件改成损坏内容）。
- 用户显式选择**「跳过有问题的附件继续导入」**时，才允许部分附件恢复；通过验证的附件仍会恢复，冲突附件跳过且不覆盖原件。`asset_issues` 逐条列出问题，界面标明“不完整”；数据库结构和行数不符仍拒绝。
- 导出侧同样如实标记：包里有"引用但磁盘上已缺失"（`<category>_missing`）或"内容与 `user_file.sha256` 不符"（`<category>_mismatched`）的附件时，导出响应带 `X-Backup-Incomplete`，界面提示"这份备份不完整"——**不要把它当成完整备份**。
- 发布或最终读回验证失败时，严格模式收回本次新建数据集和仍保持本次身份/哈希的附件；既有或已被其他写入方修改的文件保留。若磁盘或权限同时阻止回滚，应保留现场并检查日志，不能宣称故障下永远无残留。`asset_issues` 仅用于用户明确允许的部分恢复。

1. **导出**：正常时期定期在设置页导出备份包；自动备份在 `backend/data/auto-backups/<数据集>/` 下滚动保留最近 5 份快照（淘汰的移入同目录 `.trash/`，可手动捞回）。
2. **校验包**：优先使用应用内校验链，核对版本、成员路径、表结构/行数和附件 SHA-256，再公开发布；新版限制清单 4 MB、20,000 成员和配置的总解压体积。旧包没有资产 SHA-256 时走 ZIP 大小/CRC 校验，并明确验证能力差异。不要把不可信 ZIP 直接解压到业务数据目录。
3. **空目录恢复**：确认后端进程已停止；把目标数据目录中的 `resume_forge.db`（及 `-wal`/`-shm` 边车）移走留作事故现场副本，把解包出来的候选库放到 `backend/data/` 下（应用内导入则是完全自动：候选库先在临时目录迁移校验，通过后原子替换）。
4. **复核**：启动后端，核对 alembic revision 为 head；对 `manifest.json` 里记录的表行数抽查两三张核心表（岗位、简历、台账）；附件核对 `user_files/` 下清单记录的文件存在且大小一致。

**回滚点**：恢复前移走的旧库与 `-wal`/`-shm` 是唯一的现场回退点，确认新库正常前不要删。

## 5. 离线 / 模型不可用手册

未配置模型、模型服务断网或调用失败时的**实际降级行为**（以代码为准）：

| 功能 | 无模型/模型失败时的表现 |
| --- | --- |
| 岗位文本识别、资料识别、多岗位切分 | **本地解析回退**：LLM 调用失败后按本地规则解析并提示"已回退本地解析"，流程不中断 |
| 岗位需求解读（分析） | 需要 AI：未配置返回 400 提示先配置；调用失败返回 502 与固定中文文案 |
| 匹配度分析 | 未配置模型时走 `local_match_result` 本地结论（明确无模型口径）；配置了但失败返回 502 |
| 简历生成 | **必须配置模型**：未配置返回 400"请先在「设置」页配置大模型 API"；流式生成中途失败以 SSE error 事件收尾，不留"成功但无历史记录"的假状态 |
| 求职助手 | **必须配置模型**（400 提示）；回复超时/失败有预算中止与降级提示 |
| 面试深挖、复盘 | 模型失败时回退**本地汇总**（`local_review` 等），深挖照常可用 |
| 台账草拟 | LLM 草拟失败回退 `local_drafts` 本地切分（原文即原始事实） |
| 投递进度识别 | 回退本地规则（"已回退本地规则"） |
| 完全离线可用 | 岗位/简历/台账/资料的手工录入、导出、备份、回收站、提醒、投递记录管理、CSV 导入导出——全部不需要模型 |

**运营口径**：对外描述"AI 增强"时不要说成"本地智能"——降级路径是**规则回退**，产出质量低于模型路径；界面上凡是回退都有明确提示，这是 PR-11 定下的降级契约，运营文案不得越过它宣传。

## 6. 支持边界声明

- **本地单用户工具**。设计假设：一台机器、一个用户、后端只监听本机回环地址。**不支持**公网部署、多用户、多租户——这不是"暂不支持"，是架构边界：无身份认证、无用户隔离、无审计日志。
- **loopback 监听 + CORS 白名单是本地防线，不是身份认证**。它们挡的是"别的机器直接连进来"和"浏览器里其他源发起的跨站请求"，**挡不住**本机上以当前用户身份运行的任何程序。任何"部署到 NAS/服务器给家人共用"的请求都应引导到"暂无此能力"的明确回复。
- **保存位置是本机用户明确授予的文件系统能力**。目录可以在应用数据目录之外，这正是功能的用途；设置目录与弹出选择器均要求回环客户端，跨站状态变更还由 Origin 防线拒绝。目录可写性检查只创建随机命名的空探针，使用排他创建，不覆盖已有文件。因此 CodeQL 对这四个动态目录访问点的提示需按该本地授权边界复核，不能以缩小扫描范围或强制所有导出进 data 目录来“清零”。
- **专用浏览器升级后的安全参数需要新进程才生效**。新版本以固定 `about:blank` 启动，再通过 CDP 打开入口页；不再设置 `--remote-allow-origins=*`，正常客户端使用无 Origin 的本地调试连接。应用重启不会擅自终止未知/上一会话的浏览器进程：升级后请用户手动关闭旧专用窗口，再从应用重新启动。导航失败时浏览器仍保留，可检查网络后重试，不应把导航失败等同于进程未启动。
- 数据库、附件、备份、日志默认落在 `backend/data/` 与 `runtime/`，均不含向第三方上报的遥测（应用无遥测）。

## 7. 数据保留与删除说明

用户删除数据后，**哪些副本仍然存在**（对照代码实际行为；不承诺代码没有的清除能力）：

| 副本位置 | 内容 | 如何显式清除 |
| --- | --- | --- |
| 回收站（数据库内） | 岗位、简历、台账、资料箱材料、会话、内推、提醒、面经、分享包、投递记录等删除后先进回收站 | 界面「回收站」彻底删除；彻底删除后才真正出库 |
| 交付快照（数据库内） | 当时冻结的正文、目的地、版式和请求参数；删除/purge 原简历、岗位、进度不清除它 | 简历中心「交付存档」独立查找与下载；当前无应用内删除快照入口，不能把源记录 purge 当作快照清除 |
| 自动备份快照（`auto-backups/<数据集>/`，滚动 5 份 + `.trash/`） | **不可变的数据库快照**：含全部个人信息与照片引用。用户删除原简历后，删除前生成的快照里该记录仍在 | 手动删除对应快照文件（快照生成后不会被应用改写）；`.trash/` 里的同理 |
| 手动备份包（用户导出的 zip） | 同上，含导出时刻的全部数据 | 用户自行删除备份文件；应用无法触达 |
| 已导出文件（HTML/PDF/JSON/CSV 简历、导出的 CSV 岗位表） | 导出时刻的内容副本，含个人信息 | 用户自行删除导出文件 |
| 分享包 | 内容存数据库（跟着数据集与备份走），渲染出的 HTML/PDF/JSON 落在导出目录 | 界面删除分享包 + 手动删导出文件 |
| `user_files/` 附件副本 | 资料箱附件、简历照片、助手附件等的落盘副本 | 随条目删除/数据集删除处理；残留文件可在「我的文件」核对 |

**要点**：删除 ≠ 消失。"彻底删除"只保证数据库与回收站层面；**此前的备份快照与导出文件按设计是不可变副本**，要真正清除个人信息必须连同快照/备份/导出物一起删。这是面向用户的说明，客服/Issue 回复时如实转述。

## 8. 威胁模型备注（已知残留，如实记录）

- **`page_reader` 的 DNS rebinding 防护是"降低风险"而非"免疫"**（`backend/app/services/search/page_reader.py` 内有明确注释）：解析到内网/回环/保留地址会拒绝，但本机单用户工具不追求抵抗完整 DNS rebinding 链路。它读的是用户主动给的岗位 URL，攻击面是"诱导用户贴恶意链接"。
- **更新校验依赖 checksum，不依赖签名**（`backend/app/services/update_download.py`）：下载的更新包按服务端公布的 expected checksum 校验，**无代码签名验证**。checksum 源与下载源同域时，该防线防不了"服务端同时被篡改"的场景——这是当前已接受的残留风险，升级路径依赖 https 与域名/镜像主机白名单（`update_allowed_hosts`）。
- 发布 zip 无签名（§1 步骤⑥），用户侧完整性核对只有 SHA-256。
