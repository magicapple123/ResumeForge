# 验证手册：怎样才算"改好了"

> 适用场景：任何"改代码 → 声称完成"的交付，尤其是作者与复核者不是同一个人（或不是同一个模型）的时候。
> 本文只讲**判据与取证方法**，不绑定具体技术栈；命令示例用占位符表示。

## 0. 一句话

**"测试全绿"只是起点，不是证据。** 一条结论要能站住，必须满足两个条件之一：能被第三方按你写的步骤独立复算，或者你能证明"把它改坏，检查就会红"。

---

## 1. 为什么"全绿"不能作为证据

测试通过说明"在当前这套环境、这份断言、这个执行路径下没有观察到失败"。它与"功能生效"之间隔着四道缝：

| 缝隙 | 表现 | 真实后果 |
|---|---|---|
| 度量口径 | 覆盖率/性能数字取自错误的配置或错误的进程 | 数字偏差一个数量级，优化方向全错 |
| 断言空转 | 选择器匹配 0 个元素，"没有多余项"于是通过 | 缺陷被判定为已修复 |
| 桩环境 | 测试环境的几何/网络/时序与真实环境不同 | 单测全绿，真机必现 |
| 被测对象不是那一份 | 读的是旧进程、旧产物、旧缓存 | 改动根本没生效，却"验证通过" |

### 1.1 三个真实的假绿

> 以下为示意案例：细节已抽象，不提供可复算路径；要复现请按 §3 的方法在自己的仓库里造一次反证。

1. **覆盖率 41% vs 86%**：在子目录里直接跑覆盖率工具，它只从当前工作目录找配置，于是把测试代码也算进统计；显式指定仓库根配置后才是真值。数字看起来"很低"，团队据此补了一批无意义测试。
2. **空选择器假 PASS**：自查脚本写的是 `.order-control li`，真实类名是 `.rf-order-control`，`li` 匹配 0 个元素，于是"没有多余行""没有越界"全部通过。修复方式不是改断言，而是**先断言容器数量大于 0**。
3. **桩几何假绿**：拖拽逻辑在 jsdom 里连跑两轮全绿，真机上末位永远换不过去——因为测试环境的元素高度、滚动容器、`scrollTop` 夹取规则都与浏览器不同。

### 1.2 假绿的四条自检

- 这条断言**在什么情况下会红**？如果答不上来，它大概率不会红。
- 断言的**容器/根节点**是不是先被确认存在？
- 我验的是**源码、构建产物，还是打包后的分发件**？三者不能互相替代。
- 度量数字的**配置来源、进程归属、统计口径**写清楚了吗？

> 这四道缝对应的具体机理与判据见 §4–§7；本节只负责"先别信绿"。

## 2. 证据六级阶梯

给每条结论标级别，比笼统写"已验证"有用得多。

| 级别 | 证据形态 | 可信度 | 典型用途 |
|---|---|---|---|
| **L0** | 当事人自述、"我这儿是好的"、无出处的截图 | 不采信 | — |
| **L1** | 单元测试通过（含断言数） | 低 | 回归防线，不足以证明端到端行为 |
| **L2** | 结构断言：DOM/JSON/XML 的具体字段与数值 | 中 | 界面状态、接口契约 |
| **L3** | 产物原文：响应头逐字、解包后的 XML、PDF 页数、文件字节 | 高 | 导出、缓存、协议语义 |
| **L4** | 独立 oracle 复算：用另一条与实现无关的路径算出同一个数 | 高 | 页数、字数、换算、预算 |
| **L5** | 反证：把实现改坏，目标检查必红，且能逐字节复原 | 最高 | 证明"用例真的守着行为" |

三条使用规则：

1. **结论必须标注级别。** 写"L2：`aria-expanded=false`"比写"已修复"有用；写"L3：两版 JSON 的 md5 相同"比写"内容一致"有用。
2. **低级别不能替代高级别。** 10 条单测通过，不能替代一次真实产物的字节比对；反过来，一张截图也不能替代契约断言。
3. **拿不到高级别证据时，如实降级。** 正确写法是"无法复验：本机缺少 X，未取得 L3 证据"，而不是把 L1 写成"达标"。

## 3. 反证：证明用例真的守着行为

正向断言只能证明"当前产物长这样"，不能证明"这个检查能抓住回归"。反证的做法是：**临时把实现改坏，跑检查，确认它精确地红；再逐字节复原。**

### 3.1 反证三件套

| 步骤 | 要求 | 常见错误 |
|---|---|---|
| 制造破坏 | 只改一处，记录改动前后的行 | 一次改多处，红了也不知道是哪条断言起作用 |
| 确认变红 | 失败信息必须是**目标断言**，不能是导入错误/语法错误 | 看到 `ERROR` 就以为反证成功 |
| 逐字节复原 | 备份 `sha256` 一致 + 复原脚本关键字零残留 + 复跑仍绿 + `diff` 无残留 | 只把逻辑改回来，注释里的临时标记没删 |

复原证据示例（写入报告）：

```text
注掉 <实现分支> → 目标用例 2 failed（失败断言：<原文>）
注掉前 sha256 = <...>；复原后 sha256 = <...>（一致）
复跑：10 passed；grep <临时标记> → 0 命中；git diff → 仅业务改动
```

### 3.2 什么时候必须做反证

- 新增**守卫/检查脚本**：不反证就无法排除"正则失效 → 恒绿"。
- 修的是**判据类缺陷**（如"元素不存在""数值不超限"）：这类断言最容易空转。
- 交付报告里写"已修复"但**没有可观察行为**的条目。

### 3.3 反证的禁区

**不许为了让反证"红得好看"而放宽或改写断言。** 只能改断言以匹配**已确认的新行为**，并在报告里逐条列出改了哪一条、为什么。

## 4. 四类高频假绿与对应判据

### 4.1 空集断言

判据：**凡是断言"不存在 / 为空 / 没有多余项"，先断言容器数量 > 0。**

```text
先把候选集打印一次：count = N（N 必须 > 0）
再断言过滤后 count = 0
```

如果 N 本身就是 0，这条断言没有验证任何东西，必须标"未覆盖"。

### 4.2 桩环境几何

判据：**涉及布局、滚动、拖拽、媒体查询、滤镜的验收，必须在真实浏览器里量 `getBoundingClientRect()`，并写死视口尺寸。**

桩环境（jsdom 之类）没有布局引擎：`clientWidth === 0`、`scrollTop` 不会被夹取、`getComputedStyle` 对部分属性不可靠。这类用例可以留作回归防线，但不能作为验收证据。

### 4.3 mock / 注入路径可达 ≠ 用户路径可达

判据：**分别报告"后端/分支可达"与"真实入口可达"。**

典型反例：接口层已支持某状态，注入响应后界面渲染也正确，但真实控件根本产生不了这个状态——请求体里仍是旧值。正确写法是分两层：

```text
后端：达标（L3，请求体 x=... 返回 y=...）
渲染分支：达标（L2，注入后显示 ...）
真实入口：未达标（L2，控件只有 A/B/C，抓包仍是 A）
```

**验收时禁止用 `route`/拦截改写响应。** 一旦注入，验的就不再是产品。

### 4.4 度量口径

判据：**任何比率/耗时/覆盖率，必须同时给出"配置来源 + 进程归属 + 统计口径 + 样本数"。**

- 覆盖率：配置文件路径、是否包含测试代码、串行还是并行、branch 还是 line。
- 性能：冷/热、样本列表与中位数、是进程内还是含网络、是上界还是净成本。
- 单次读数是不可复现的证据；至少给中位数与样本。

## 5. 判据要可证伪

**"元素存在"不是判据，"元素满足某个可证伪的谓词"才是。**

| 差的判据 | 好的判据 | 为什么 |
|---|---|---|
| 不存在下边框元素 | 下边框颜色 ≠ 强调色 | 该元素可能本来就是"内边距装置"，按"不存在"会误判正常设计为缺陷 |
| 文案正确 | 目标语言下无中文残留，且断行位置与基准一致 | "正确"无法判定 |
| 不溢出 | `scrollWidth == clientWidth` 且各元素 `rect.right <= 容器.right` | 可机检 |
| 时间对 | 与已知基准时区换算一致（含跨午夜用例） | 覆盖边界 |

两条补充：

- **文本检查要取上下文。** `includes("上限 1 页")` 会把选项列表本身当成缺陷文案；应定位到承载该语义的节点。
- **数值要给换算与单位。** "间距 4"是 4px、4 倍字号还是 4%？判据里必须写清，否则下一轮会被重新解释。

## 6. 反向态回归

**修"允许 X"的票，必须同时验"不允许 X 时行为不变"。** 否则把功能删掉也能全绿。

标准三段：

```text
正向：X 打开 → 期望行为 A
反向：X 关闭 → 期望行为 B（与改动前逐值一致）
中间态：X 处于边界值 → 行为可解释（不是崩溃、不是静默）
```

实例：某"不限上限"能力上线后，必须回测上限为 1、为 2 时的截断提示、导出页数、响应头三者都未变；只测"不限"通过，等于没验。

---

## 7. 先证明"验的是这份代码"

在怀疑逻辑之前，先排除"读到的不是新代码"。按顺序核三段：

| 段 | 核对方法 | 不一致时的结论 |
|---|---|---|
| 进程 | 监听端口的是哪个 PID、启动时间是否晚于最后一次改动 | 旧进程仍在服务，所有现象无效 |
| 产物 | 磁盘入口文件的 `sha256` 是否等于 HTTP 取回的同一文件 | 服务读的是另一个目录/另一份包 |
| 缓存 | 新旧产物字节差异数（`cmp -l`）、体积是否相同 | 等长替换≠没重建；`git status` 干净≠包是新的 |

**产物目录通常不进版本库**，所以"工作区干净"完全不能证明分发包是新的。判定顺序固定为：源码标记 → 构建入口 hash → 服务返回的入口 → 用报错里出现的 chunk 名去产物目录 grep。

## 8. 验收本身会产生副作用

改数据的验收脚本必须自带三件事：

1. **快照/复原**：走接口取原始值，结束后按原值写回，不依赖 UI。
2. **显式 id**：被操作对象的 id 必须传参，不能依赖脚本里的默认值（并行时会改到别人那份）。
3. **可复原边界**：数据状态要复原，**审计痕迹不要伪造**。版本号/修订号因真实写入而递增，属于事实，不应回滚；正文内容用内容哈希证明"一个字节没变"。

验收报告单列一节"本报告造成的数据变更"，写清：改了哪些记录、当前版本号、哪些字段无法复原（以及原因）。

---

## 9. 结论四态与报告写法

不要用"达标/不达标"两态，会逼着人把"没验"写成"达标"。用四态：

| 状态 | 含义 | 报告要求 |
|---|---|---|
| **达标** | 有 L2 以上证据，且反向态已验 | 给数据与路径 |
| **部分可验** | 主路径达标，某个分支受数据/环境限制未触发 | 写清哪一项没触发、为什么、怎么补 |
| **未覆盖** | 没做 | 写清缺口与风险 |
| **无法复验** | 环境不具备（缺字体、缺真实引擎、缺设备） | **写在正文，不写脚注** |

报告的硬规则：

- 每个结论后面要么有命令输出、要么有文件路径、要么有可复算的数字；禁止"优化了体验""性能更好"这类无法复核的说法。
- "未完成"与"风险"各自成节，不能合并成一句"部分场景未覆盖"。
- 已知问题要归属：**既有问题**还是**本批引入**。用 `git diff --stat` 证明文件未被本批触碰，比口头声明有力。

## 10. 一页检查表

- [ ] 每条结论都标了证据级别（L0–L5）
- [ ] 所有"不存在/为空"断言都先证明了容器数量 > 0
- [ ] 布局/拖拽类结论来自真实浏览器，写明了视口
- [ ] 度量数字带了配置来源、进程归属、口径、样本
- [ ] 新增/修改的守卫做过反证，且有逐字节复原证据
- [ ] 修"允许 X"的条目，反向态也验了
- [ ] 确认过进程、产物、缓存三段对齐
- [ ] 验收脚本有快照/复原，且 id 显式传参
- [ ] 报告区分了"完成"与"已证明"，未达标写了三件套（为什么取不到 / 替代证据 / 还差什么）
- [ ] 没有用放宽断言、隐藏溢出、跳过截图的方式"变绿"
