# 与 AI 协作的作业规程

> 适用场景：把一个多步骤改动交给 AI 执行（单会话或多会话/多智能体），需要它**不用反复追问、也不会把半成品当完成**的时候。
> 不适用：一次性问答、探索性调研、没有验收标准的开放任务。

## 0. 核心判断

**AI 执行失败，多数不是"能力不够"，而是"任务书没写清边界、验收没有判据、并行没有隔离"。** 这三件事都能在开工前解决，成本远低于返工。

---

## 1. 三个角色与信息流

| 角色 | 职责 | 不该做什么 |
|---|---|---|
| **编排者** | 拆任务、分派、裁决冲突、汇总验收 | 不替执行者写实现细节，不跳过验收 |
| **执行者** | 按文件所有权改代码，自验，按格式回报 | 不跨界改别人的文件，不改验收标准 |
| **复核者** | 独立复跑、给证据级别、挑反例 | 不复用执行者的截图与结论 |

**跨角色的信息必须经编排者中转。** 执行者之间的口头约定不会进任何文档，换一批人（或换一个会话）就失效。

---

## 2. 任务书：让执行者不用猜

一份能被直接执行的任务书，固定九节：

| # | 小节 | 必须写什么 | 漏了会怎样 |
|---|---|---|---|
| 1 | 用途与边界 | 交给谁、一次性还是分批、**只改列出的项** | 范围蔓延，顺手重构 |
| 2 | 唯一事实来源 | 以哪份文档为准；文档很长时指明"读第几节" | 执行者按过期清单开工 |
| 3 | 红线 | 5–6 条最易踩的：不提交、不动迁移、不硬删、不改他人文件 | 一次违规就回退全部产出 |
| 4 | 环境 | 怎么起服务、用哪个解释器、端口/数据目录、如何重建产物 | 对着旧进程验证，白跑一轮 |
| 5 | 任务表 | `# | 标题 | 影响文件 | 依赖 | 一句话验收` | 排期靠猜，冲突靠撞 |
| 6 | 逐条正文 | 现象（带数字）→ 根因（文件:行）→ 方案 → **坑** → 验收 | "改了但没修好" |
| 7 | 返工规则 | 轮次上限、到限动作、什么情况必须停下上报 | 无限循环或带病交付 |
| 8 | 并行方案 | 按**文件所有权**分组，标串行顺序与独占项 | 后写覆盖先写 |
| 9 | 回报格式 | 一行一条的固定字段 + 汇总 | 汇报无法比对、无法汇总 |

### 2.1 验收要写成"可判真假"

| 不可执行 | 可执行 |
|---|---|
| 看起来更清爽 | 该区块高度从 195px 降到 ≤60px |
| 拖拽正常 | 落点指示线宽 3px，`dragover` 被接管，松手后顺序数组等于期望值 |
| 时间正确 | 与基准时区换算一致，含 23:50 跨午夜用例 |
| 兼容旧数据 | 新字段全为 null 时，四份产物指纹与改前逐字节一致 |

### 2.2 必须写"坑"

每条任务的"坑"是**上一轮踩过并撤销的决定**。没有这一节，下一个人会以"更彻底"为名改回去。

示例句式：

> 不要在这里用 `dropEffect="none"`：它会吞掉 `drop` 事件，导致"拖了没反应"。上一轮就是因此撤销的；若要保留禁止光标，必须同时把提示挪到 `dragend`。

### 2.3 必须写"明确不做"

方案段落后追加一句"本条不做 X，因为 Y；若要做，需要 Z 条件"。否则下一轮会重新提出同一方案，或者执行者顺手做多。

---

## 3. 清单与施工单分开

当条目超过 ~20 条，一份文档会同时承担"诊断记录"和"排期表"，两边都做不好。拆成两份：

| 文档 | 只回答 | 读者 | 体量 |
|---|---|---|---|
| **问题清单** | 这是什么缺陷、根因是什么、怎么验收 | 想理解问题的人 | 可以很长（千行级） |
| **施工单** | 先做哪条、谁做、怎么算做完、怎么证明 | 执行者 | 必须短，一屏能扫 |

施工单里每行末尾放"一句话验收"，让排期与 DoD 在同一张表里可见；详细诊断用链接指回清单，不复制。

---

## 4. 并行只能按文件所有权切

**并行安全的唯一边界是"文件不重叠"，不是"任务不相关"。**

两个任务在语义上无关，只要改同一个文件，就必然出现"后写覆盖先写"。分组的正确姿势：

| 组 | 负责文件 | 串行顺序 | 独占 |
|---|---|---|---|
| A | 左栏组件 + 其样式 | 1 → 6 → 4 | — |
| B | 中栏组件 + 拖拽逻辑 | 5 → 7 → 8 | — |
| 编排者 | 产物重建、全量测试、`CHANGELOG`、`docs/**`、共享语言包 | — | 是 |

四条硬规则：

1. **共享文件单点写入。** 语言包、路由表、schema 索引这类"谁都要加一行"的文件，由编排者统一落，执行者在回报里列出需要的 key。
2. **同文件多任务批内串行。** 不要靠"注意不要冲突"的提醒，要写进排期。
3. **用户可感知的行为变更独占一批。** 否则回归时说不清"是这批改的还是上批改的"。
4. **执行者禁止"顺手改一下"跨组文件。** 需要改就回报，由编排者裁决。

### 4.1 所有权表模板

```text
组 A（左栏/页眉）：components/header/*、styles/header.css
组 B（中栏/拖拽）：components/editor/*、features/drag/*
编排者独占：dist 重建、全量测试、CHANGELOG.md、docs/**、i18n/messages/**
共享文件：i18n 语言包 —— 谁需要新 key 先在回报里列出，由编排者统一落
```

同时列出**行数/体积余量**：把"这个文件只剩 2 行预算"写在开工前，比事后拆文件便宜。

## 5. 脏工作区纪律

多会话并行时，工作区里通常有别人未提交的改动。此时：

| 禁止 | 原因 | 替代做法 |
|---|---|---|
| `git checkout -- <file>` | 会连同他人未提交改动一起回滚 | 改前把目标文件复制到快照目录，返工时覆盖回来 |
| `git stash` / `git restore` | 同上，且恢复顺序不可控 | 同上 |
| `git reset --hard` | 整仓回滚，等同事故 | 永不使用 |
| 全仓格式化 | 重排数百个存量文件，淹没真实 diff | 只格式化本次新增/修改的文件 |

**改前快照**的具体做法：

```text
mkdir -p <snapshot_dir>/<task>
cp --parents <你要改的每个文件> <snapshot_dir>/<task>/
```

回退时按文件覆盖，不用 git。交付前用 `git status --porcelain <自己的文件>` 确认仍是"已修改"而不是被谁覆盖。

改动叠加在同一文件时，回退必须**按 hunk**：先 `git diff -U0` 看清每个 hunk 的位置，再决定回退哪一段。

## 6. 基线三件套

开工前必须记录，否则事后无法区分"我改红了"与"本来就红"：

| 项 | 怎么记 | 用途 |
|---|---|---|
| 代码基线 | `HEAD` 短 hash + 分支 | 报告里所有"改前/改后"都相对它 |
| 工作区状态 | `git status --porcelain \| wc -l`、哪些是别人的 | 证明你没提交别人的半成品 |
| 测试基线 | 后端 `passed/failed/skipped` + 前端 `files/tests/Errors` | 失败项归属 |

基线红了要**写明归属**：

> 后端 1 failed / `<N>` passed。失败项是行数守卫（某文件超出预算 `<M>` 行），由在途改动引入，**不是本批**。

覆盖率基线单独记：串行跑、注明配置来源、注明是否含测试代码。

---

## 7. 交接与续跑

会话中断（额度、超时、换人）后，接续的第一步不是读需求，而是**核对落盘现状**：

1. `git status` / `git diff --stat`：改到哪一步；
2. 文件行数与关键函数是否存在：有没有半截实现；
3. 静态检查与相关用例能否跑通：是不是"看起来写完了但编译不过"；
4. 服务与产物时间戳：验证环境是不是新的。

四步都过，才继续；任何一步对不上，先把现状写进进度表，再决定重做还是续做。

### 7.1 子任务"完成"必须主控核验

执行者（尤其是子智能体）回报"已完成"时，**不等于磁盘上真的有了**。核验三件：

- 文件是否存在、行数是否合理；
- 静态检查是否 0 错；
- 它声称跑过的命令，输出是否真的贴出来了。

核验不过就退回，不接受"应该没问题"。

---

## 8. 返工上限与回报格式

- **轮次上限 2–3 轮**。到限仍不过，标"阻塞"，写清：卡在哪一步、试过什么、需要谁做什么决定，然后继续下一条。
- **禁止改验收标准来通过**。只能改断言以匹配已确认的新行为，并在报告里逐条列出。
- 回报固定一行，便于汇总：

```text
[任务 N] 状态：通过/未通过/阻塞 | 改动：<文件> | 证据：<路径或命令> | 返工：<次数> | 备注：<需编排者处理的事>
```

---

## 9. 进度表要可信

字段设计与填写纪律同样重要。最小字段：

| 列 | 要求 |
|---|---|
| `#` / 标题 | 与施工单编号一致 |
| 状态 | 固定枚举：未开始 / 进行中 / 完成 / 阻塞 |
| **证据** | 截图路径或命令输出；**标"完成"必须同时填这一列** |
| 返工次数 | 有返工就写，全 0 反而是危险信号 |
| 备注 | 只放阻塞原因与依赖 |

两条纪律：

1. **状态与证据同填。** "27 条全完成、截图列全空"不是效率高，是证据缺失。
2. **批次日志按批号分区，不要纯追加。** 追加式日志很快会乱序，无法按批回溯。

## 10. 交付报告：偏差前置

报告的头等任务不是汇报完成率，而是**让读者知道哪里和预期不一样**。

推荐结构：

```text
§0 元信息：依据文件、基线 commit、工作区状态、验证环境、日期
§1 结论 + 最需要你知道的三件事（口径变更 / 契约变更 / 环境陷阱）
§2 完成情况总表：状态 / 改动文件 / 证据 / 偏差指针
§3 逐条证据：改动 → 步骤 → 数据 → 证据路径 → 结论
§4 回归结果：passed/failed、覆盖率及口径、静态检查、产物一致性、基线对照
§5 未完成与差距：为什么取不到 / 替代证据 / 还差什么 / 是否已被用例守住
§6 偏差与兼容性：要求 / 实际做法 / 原因 + 数据/接口/交互/语义四层影响
§7 风险与没跑的关卡
§8 用户自验清单：打开哪页 → 点什么 → 应看到什么
§9 回滚方式：逐文件，禁整仓回滚
§10 执行过程偏差与事故：守卫变红及修法、中断与续跑、误操作与流程修正
```

硬规则：**"未达标"必须写三件套**——为什么取不到、替代证据是什么、还差什么才算完成。只说"未验证"是含糊；说清三件才是披露。

## 11. 一页检查表

开工前：

- [ ] 有一份九节齐全的任务书，验收可判真假
- [ ] 条目按文件所有权分组，共享文件已指定单点写入人
- [ ] 记录了 HEAD、脏改动数、测试基线
- [ ] 明确了禁 commit / 禁迁移 / 禁硬删等红线
- [ ] 环境（解释器、端口、数据目录、产物重建）写进文档

执行中：

- [ ] 改前做了文件快照，没有用 git 回滚
- [ ] 每条改完立刻跑相关用例与类型检查，没有攒到最后
- [ ] 跨组文件改动先回报，没有"顺手改"

收尾：

- [ ] 进度表的状态列与证据列同时填了
- [ ] 报告偏差前置、未达标写满三件套
- [ ] 子任务"完成"都已由主控核验过
- [ ] 交付前确认过"我提交的文件"与"我以为提交的文件"一致
