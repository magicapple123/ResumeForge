# 与 AI 协作的作业规程

> 适用场景：把一个多步骤改动交给 AI 执行（单会话或多会话/多智能体），需要它**不用反复追问、也不会把半成品当完成**的时候。
> 不适用：一次性问答、探索性调研、没有验收标准的开放任务。

## 0. 核心判断

**AI 执行失败，多数不是"能力不够"，而是"任务书没写清边界、验收没有判据、并行没有隔离"。** 这三件事都能在开工前解决，成本远低于返工。

---

## 1. 三个角色与信息流

| 角色 | 职责 | 不该做什么 |
|---|---|---|
| **编排者** | 拆任务、分派、裁决冲突、汇总验收 | 不替执行者写实现细节，不跳过验收 |
| **执行者** | 按文件所有权改代码，自验，按格式回报 | 不跨界改别人的文件，不改验收标准 |
| **复核者** | 独立复跑、给证据级别、挑反例 | 不复用执行者的截图与结论 |

**跨角色的信息必须经编排者中转。** 执行者之间的口头约定不会进任何文档，换一批人（或换一个会话）就失效。

---

## 2. 任务书：让执行者不用猜

一份能被直接执行的任务书，固定九节：

| # | 小节 | 必须写什么 | 漏了会怎样 |
|---|---|---|---|
| 1 | 用途与边界 | 交给谁、一次性还是分批、**只改列出的项** | 范围蔓延，顺手重构 |
| 2 | 唯一事实来源 | 以哪份文档为准；文档很长时指明"读第几节" | 执行者按过期清单开工 |
| 3 | 红线 | 5–6 条最易踩的：不提交、不动迁移、不硬删、不改他人文件 | 一次违规就回退全部产出 |
| 4 | 环境 | 怎么起服务、用哪个解释器、端口/数据目录、如何重建产物 | 对着旧进程验证，白跑一轮 |
| 5 | 任务表 | `# | 标题 | 影响文件 | 依赖 | 一句话验收` | 排期靠猜，冲突靠撞 |
| 6 | 逐条正文 | 现象（带数字）→ 根因（文件:行）→ 方案 → **坑** → 验收 | "改了但没修好" |
| 7 | 返工规则 | 轮次上限、到限动作、什么情况必须停下上报 | 无限循环或带病交付 |
| 8 | 并行方案 | 按**文件所有权**分组，标串行顺序与独占项 | 后写覆盖先写 |
| 9 | 回报格式 | 一行一条的固定字段 + 汇总 | 汇报无法比对、无法汇总 |

### 2.1 验收要写成"可判真假"

| 不可执行 | 可执行 |
|---|---|
| 看起来更清爽 | 该区块高度从 195px 降到 ≤60px |
| 拖拽正常 | 落点指示线宽 3px，`dragover` 被接管，松手后顺序数组等于期望值 |
| 时间正确 | 与基准时区换算一致，含 23:50 跨午夜用例 |
| 兼容旧数据 | 新字段全为 null 时，四份产物指纹与改前逐字节一致 |

### 2.2 必须写"坑"

每条任务的"坑"是**上一轮踩过并撤销的决定**。没有这一节，下一个人会以"更彻底"为名改回去。

示例句式：

> 不要在这里用 `dropEffect="none"`：它会吞掉 `drop` 事件，导致"拖了没反应"。上一轮就是因此撤销的；若要保留禁止光标，必须同时把提示挪到 `dragend`。

### 2.3 必须写"明确不做"

方案段落后追加一句"本条不做 X，因为 Y；若要做，需要 Z 条件"。否则下一轮会重新提出同一方案，或者执行者顺手做多。

---

## 3. 清单与施工单分开

当条目超过 ~20 条，一份文档会同时承担"诊断记录"和"排期表"，两边都做不好。拆成两份：

| 文档 | 只回答 | 读者 | 体量 |
|---|---|---|---|
| **问题清单** | 这是什么缺陷、根因是什么、怎么验收 | 想理解问题的人 | 可以很长（千行级） |
| **施工单** | 先做哪条、谁做、怎么算做完、怎么证明 | 执行者 | 必须短，一屏能扫 |

施工单里每行末尾放"一句话验收"，让排期与 DoD 在同一张表里可见；详细诊断用链接指回清单，不复制。

---

## 4. 并行只能按文件所有权切

> **§4–§8 的定位**：可执行步骤以 `AGENTS.md` 的「多会话并行」一节为权威，这几节只写理由、本仓库特有约束与容易漏的判据；两边冲突时以 AGENTS.md 为准。

**并行安全的唯一边界是"文件不重叠"，不是"任务不相关"。** 语义上无关的任务只要改同一个文件，就必然出现"后写覆盖先写"；分工表与"共享文件单点写入"的写法见 [`templates/task-brief.md`](templates/task-brief.md) §8，不再另抄一份。三条容易漏的：同文件多任务**批内串行**（写进排期，不靠"注意不要冲突"的口头提醒）；**用户可感知的行为变更独占一批**（否则回归时说不清是谁引入的）；执行者**禁止"顺手改一下"跨组文件**，需要改就回报，由编排者裁决。

### 4.1 所有权表模板

开工前写清三件事：组别与文件清单、组内串行顺序、共享文件由谁单点写入（填写样式见 task-brief §8）。同时列出每个文件的**行数/体积余量**——"这个文件只剩 2 行预算"写在开工前，比事后拆文件便宜。

---

## 5. 脏工作区纪律

并行时工作区常有别人未提交的改动，**禁止用 git 回滚**：`git checkout -- <file>` / `git stash` / `git restore` 会连带回滚他人改动，`git reset --hard` 等同事故；全仓格式化会重排数百个存量文件、淹没真实 diff，只格式化本批改到的文件。

**改前快照**：把目标文件复制到**仓库外**的目录（如 `D:/rf_snapshots`）并保持相对路径——放进仓库会污染 `git status`，也可能被批量删除守卫拦下。

```bash
mkdir -p <snapshot_dir>/<task> && cp --parents <你要改的每个文件> <snapshot_dir>/<task>/   # `--parents` 是 GNU 扩展：Git Bash 支持，macOS 的 BSD cp 不支持
```

PowerShell 没有 `--parents`：对每个文件先 `New-Item -ItemType Directory -Force (Split-Path $dst)` 建好相对目录，再 `Copy-Item`。

回退按文件覆盖、不用 git；同一文件多轮改动叠加时先 `git diff -U0` 看清 hunk 分布再按段回退。交付前用 `git status --porcelain <自己的文件>` 确认仍是"已修改"而不是被谁覆盖。

---

## 6. 基线三件套

开工前记三项：`HEAD` 短 hash + 分支、`git status --porcelain` 的条数及归属、相关测试的 `passed/failed/skipped`（前端另记 `files/tests/Errors`）。否则事后无法区分"我改红了"与"本来就红"。

基线红了要**写明归属**，例如：`后端 1 failed / <N> passed`，失败项是行数守卫（某文件超出预算 `<M>` 行），由在途改动引入，**不是本批**。覆盖率基线单独记：串行跑、注明配置来源、注明是否含测试代码。

---

## 7. 交接与续跑

会话中断（额度、超时、换人）后，接续的第一步不是读需求，而是**核对落盘现状**：

1. `git status` / `git diff --stat`：改到哪一步；
2. 文件行数与关键函数是否存在：有没有半截实现；
3. 静态检查与相关用例能否跑通：是不是"看起来写完了但编译不过"；
4. 服务与产物时间戳：验证环境是不是新的。

四步都过，才继续；任何一步对不上，先把现状写进进度表，再决定重做还是续做。

### 7.1 子任务"完成"必须主控核验

执行者（尤其是子智能体）回报"已完成"，**不等于磁盘上真的有了**。核验三件：文件是否存在且行数合理、静态检查是否 0 错、它声称跑过的命令是否真的贴出了输出。核验不过就退回，不接受"应该没问题"。

---

## 8. 返工上限与回报格式

- **轮次上限 2–3 轮**。到限仍不过，标"阻塞"，写清：卡在哪一步、试过什么、需要谁做什么决定，然后继续下一条。
- **禁止改验收标准来通过**。只能改断言以匹配已确认的新行为，并在报告里逐条列出。
- 回报格式见 `AGENTS.md` 的「回报固定一行」，字段与顺序照它；汇总另附通过数、未通过数、未覆盖风险、产物是否重建。

---

## 9. 进度表要可信

字段设计与填写纪律同样重要。最小字段：

| 列 | 要求 |
|---|---|
| `#` / 标题 | 与施工单编号一致 |
| 状态 | 固定枚举：未开始 / 进行中 / 完成 / 阻塞 |
| **证据** | 截图路径或命令输出；**标"完成"必须同时填这一列** |
| 返工次数 | 有返工就写，全 0 反而是危险信号 |
| 备注 | 只放阻塞原因与依赖 |

两条纪律：

1. **状态与证据同填。** "27 条全完成、截图列全空"不是效率高，是证据缺失。
2. **批次日志按批号分区，不要纯追加。** 追加式日志很快会乱序，无法按批回溯。

---

## 10. 交付报告：偏差前置

报告的头等任务不是汇报完成率，而是**让读者知道哪里和预期不一样**；三条不能省：

1. **偏差前置**：结论先写"最需要你知道的三件事"（口径变更 / 契约变更 / 环境陷阱），总表每条都带偏差指针。
2. **证据优先**：每条结论后面跟命令输出、文件路径或可复算的数字；"完成"必须同时有证据。
3. **未完成要写清**：每条**四要素**——为什么取不到、替代证据是什么、还差什么才算完成、**是否已被用例守住**。只说"未验证"是含糊，写全四要素才是披露。

§0–§10 的完整结构、表格字段与填写要求见 [`templates/delivery-report.md`](templates/delivery-report.md)；两处同源，以模板为准。

---

## 11. 一页检查表

开工前：

- [ ] 有一份九节齐全的任务书，验收可判真假
- [ ] 条目按文件所有权分组，共享文件已指定单点写入人
- [ ] 记录了 HEAD、脏改动数、测试基线
- [ ] 明确了禁 commit / 禁迁移 / 禁硬删等红线
- [ ] 环境（解释器、端口、数据目录、产物重建）写进文档

执行中：

- [ ] 改前做了文件快照，没有用 git 回滚
- [ ] 每条改完立刻跑相关用例与类型检查，没有攒到最后
- [ ] 跨组文件改动先回报，没有"顺手改"

收尾：

- [ ] 进度表的状态列与证据列同时填了
- [ ] 报告偏差前置、未达标写满四要素（含"是否已被用例守住"）
- [ ] 子任务"完成"都已由主控核验过
- [ ] 交付前确认过"我提交的文件"与"我以为提交的文件"一致
