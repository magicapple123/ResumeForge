# ADR-0005：备份恢复「先验后发布」与附件防覆盖

日期：2026-10-14（1.0 复验 RR-03）
状态：已实施

## 背景

复验实证了三件事，都发生在同一条链路上：

1. `restore_assets_from_manifest` 以 `target.open("wb")` **直接写**共享的
   `datasets/user_files`、`referral_images`，**写完才**读回来核对 sha256。包内同名成员
   被改过（甚至只是自洽篡改、连清单一起改）时，本机已有的同名附件会被覆写成损坏内容，
   而问题只是被记进返回的 `asset_issues`。
2. `import_dataset` 在**附件校验之前**就发布了主库与随包数据集；附件问题最终只是 200
   成功响应里的提示（前端此前根本没读这个字段），与用户指南"整包要么全成、要么不动"
   的承诺不符。
3. 多份数据集共用同一个磁盘资产目录，包内前缀不同也挡不住物理同名——只有逐文件比对
   内容才能发现冲突。

## 决策

**把顺序倒过来：先验后发布，绝不覆盖本机文件。**

- **阶段一（只读预检 + 私有暂存）**：附件逐个从包内流式读出并同时计算 sha256，与清单
  核对成员存在性、大小、哈希与文件名合法性；随后与本机现状做冲突检测——同名同内容算
  "已满足"，同名不同内容记为冲突，包内跨段同名但内容不同同样记为冲突。通过的字节写进
  导入暂存目录（`.rf-restore-<随机>`），**目标目录一个字节都没写**。
- **默认 fail-closed**：完整性问题（缺成员/哈希不符/非法文件名）或冲突存在时，整次导入
  以 4xx 失败并给出第一条原因，什么都不写。用户**显式**选择
  `allow_partial_assets`（界面：确认弹窗「跳过有问题的附件继续导入」）才继续，
  被跳过/冲突的附件逐条进 `asset_issues`，结果标 `assets_incomplete`。
- **阶段二（发布）**：全部通过后先原子发布库（`.partial` → rename），再逐文件
  `os.replace` 原子发布附件；发布前再查一次同名（预检到发布之间可能有人写入），内容不同
  就保留本机文件并报冲突。
- **回滚**：发布链路任何失败都收回**本次新建**的数据集文件（主文件 + 边车 + 元信息）。
  用户既有文件一律不动——回滚绝不删除用户数据。
- **独立复核**：收尾用 `verify_restored_assets` 以**磁盘现状**对照清单再核一遍
  （不依赖恢复过程的内存状态）；行数复核 (`verify_database_rows`) 同样照旧。
- **导出侧如实标记**：清单新增 `<category>_mismatched`（磁盘字节与 `user_file.sha256`
  不符），响应头带 `X-Backup-Incomplete` / `X-Backup-Asset-Warnings`，界面把"已导出"
  改成"这份备份不完整"。不完整的包不许被当成完整备份。

## 后果

- 老格式包（无 `asset_manifest`）保持兼容：仍走"遍历扁平成员、跳过同名"的老路径——它
  从不覆盖本机文件，保护性与新路径一致。
- 附件恢复不再是"顺带尽力而为"：它和库一样有预检、有回滚、有失败语义。用户显式选择
  部分导入时，代价（哪些附件没恢复）必须可见。
- 新增写盘前的额外读数（每个附件读两遍：预检一遍、发布后复核一遍）。附件是用户文件，
  量级远小于 `manifest.json` 记录的表行数操作，可接受。
- 共享扁平资产目录的**物理**同名问题被拦住了，但没有从结构上消除（改名会破坏旧包与
  既有数据）。这是有意的取舍：先保证"绝不损坏既有文件"。
